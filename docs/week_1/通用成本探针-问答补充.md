# 通用成本探针:问答补充

> 来源:一次围绕 [`通用成本探针.md`](通用成本探针.md)、[`cost_probe.py`](../../cost_probe.py) 和服务器长跑数据的追问整理。
> 目的:把“探针脚本到底在测什么”“服务器数据有什么用”“怎么写打卡”拆开讲清楚。

---

## 1. `cost_probe.py` 这个探针脚本是做什么的?

[`cost_probe.py`](../../cost_probe.py) 不是交易脚本,不会下单,也不需要钱包里有钱。它只调用 LI.FI 的只读报价接口,回答一个问题:

```text
如果我现在走这条路径,实际能拿回多少?
中间有哪些费用?
要有多大的价差,才刚好不亏?
```

你可以把它理解成“套利前的成本雷达”。

例如你想做:

```text
Arbitrum 上发出 10,000 USDC
跨到 Base
最后还是拿 USDC
```

如果 LI.FI 报价说:

```text
发出 10,000 USDC
到手 9,975 USDC
```

那么在还没看市场价差之前,这条路已经先亏:

```text
10,000 - 9,975 = 25 USDC
25 / 10,000 = 0.25% = 25 bps
```

结论:

```text
Base 上的真实可成交价格至少要比 Arbitrum 高 25 bps,
这条路才刚好回本。
```

所以探针脚本测的不是“赚了多少钱”,而是:

```text
这条路的最低回本门槛是多少 bps?
```

---

## 2. 文档里几个关键词是什么意思?

### 真实门槛

这条路径最低需要多少毛价差才能回本。

例如真实门槛是 `25 bps`,意思是:

```text
屏幕上的价差必须大于 25 bps,
这条路径才可能赚钱。
```

如果价差只有 `10 bps`,那不是“小赚”,而是:

```text
10 bps - 25 bps = -15 bps
```

稳定亏。

### 硬成本

可以用同一种 token 数量直接相减的成本。

例如:

```text
10,000 USDC - 9,975 USDC = 25 USDC
```

这部分最可信,因为不需要美元价格、不需要估值、不需要猜。

### 账外成本

gas、未包含费用等,通常用原生币支付,例如 ETH / BNB。

这些费用要折算回 USDC,只能用价格,所以它是估算。脚本把它单独列出来,避免把“硬事实”和“估算”混在一起。

### bps

`bps` 是基点:

```text
1 bps  = 0.01%
25 bps = 0.25%
60 bps = 0.60%
```

## 3. 为什么跨资产要用 `--roundtrip`?

同资产路径可以直接减:

```text
10,000 USDC -> 9,975 USDC
成本 = 25 USDC
```

但跨资产路径不能直接减:

```text
10,000 USDC -> 5.34 WETH
```

因为:

```text
10,000 USDC - 5.34 WETH = ?
```

单位不同,这个减法没有意义。

所以脚本用 `--roundtrip` 把路径闭合回起点资产:

```text
10,000 USDC -> 5.34 WETH -> 9,957.78 USDC
```

这样起点和终点又都是 USDC,就能诚实计算:

```text
10,000 - 9,957.78 = 42.22 USDC
成本 = 42.2 bps
```

这就是文档说的:

```text
套利是环,所以成本也该按环算。
```

## 4. 它和服务器上跑的数据是什么关系?

关系是:

```text
cost_probe.py = 单次测量仪器
watch_probe.py = 把这个仪器放到服务器上,每半小时自动测一次
watch/*.jsonl = 服务器长期测出来的历史样本
```

Week 1 的《通用成本探针》先解决“怎么算”:

```text
一条路径的真实门槛 = 硬成本 bps + 账外成本 bps
跨资产路径必须 roundtrip 闭环
同资产数量相减才可信
```

Week 2 的服务器长跑解决“常态是什么”:

```text
一次报价只是一个点
连续报价才是一组分布
分布才能支撑判断
```

所以服务器没有换算法。它只是把:

```text
手动跑一次 cost_probe.py
```

变成:

```text
每半小时跑一次 cost_probe.py
持续跑几十小时
积累几十到上百次观测
```

## 5. 为什么文档要更正“3 个采样点不代表常态”?

早期手动跑跨资产往返路径时,看到过这类数字:

```text
1,000 USDC    29.41 bps
10,000 USDC   36.11 bps
```

这些数字本身是真的,是当时 LI.FI 的真实报价。

问题是:它们只是很少的采样点。

后来服务器连续跑了 48.5 小时、98 次观测,发现真实分布是:

```text
1,000 USDC    中位 60.45 bps   区间 [51.90, 73.31]
10,000 USDC   中位 60.84 bps   区间 [44.89, 70.52]
```

于是早期概括:

```text
这条跨资产路径大概是 30 bps 级别
```

被更正为:

```text
这条跨资产路径常态约 60 bps,不是 30 bps。
```

这不是 `cost_probe.py` 算错了,而是样本太少时,人从数字里读出了错误概括。

更准确的复盘是:

```text
数字是真的。
错的是“这几个数字代表常态”这句话。
```

## 6. “如果真实可成交价差长期小于 60 bps,这条路径稳定地过不了成本门槛”是什么意思?

意思是:

```text
这条路平均要先付出约 60 bps 成本。
如果市场上能看到、并且真的能成交的价差长期不到 60 bps,
那每次做这条套利都是负收益。
```

净收益可以粗略写成:

```text
净收益 = 真实可成交价差 - 真实成本门槛
```

如果成本门槛是 `60 bps`,而价差是:

```text
20 bps
30 bps
50 bps
```

都不够。

例如:

```text
40 bps - 60 bps = -20 bps
```

这就是亏。

只有当真实可成交价差大于 60 bps,例如:

```text
80 bps - 60 bps = +20 bps
```

它才有可能赚钱。

这里的“真实可成交价差”很重要。它不是网页上随便显示的标价差,而是你这个规模真的买进去、卖出来之后还能保留的价差。屏幕价差可能显示 80 bps,但一成交就被滑点、深度、路由吃掉,最后实际可能只剩 30 bps。

所以更直白地说:

```text
这条路的过路费约 60 bps。
如果路上能捡到的钱长期少于 60 bps,
那就稳定亏钱。
```

## 7. 这组服务器数据在后续学习里有什么用?

### 1. 过滤无效路径

如果一条路径常态成本是 `60 bps`,以后看到 `20~40 bps` 的价差,可以直接过滤。

这不是“今天没机会”,而是:

```text
这个量级的价差根本过不了成本门槛。
```

### 2. 填证据记录表

`watch/*.jsonl` 是采样,`evidence.csv` 是判断。

这组数据可以支撑证据记录表里的:

```text
观测次数
真实成本bps
路径分布
延迟秒
可复现?
成败原因
```

如果后续补上的真实可成交价差长期低于成本门槛,可以把结论写成:

```text
可复现地不成立
```

### 3. 训练“不要用一次报价下结论”

这组数据最大的价值不是“发现 60 bps”,而是证明:

```text
3 个采样点会把结论带偏。
一个数字是采样,一个分布才是观察。
```

这条教训可以迁移到后续所有策略验证。

### 4. 给完整成本模型打底

目前的 60 bps 只包含:

```text
报价成本 + gas/未含费
```

还没包含:

```text
执行延迟期间价差消失
失败交易概率
资金占用
路由切换风险
上游数据异常可信度折扣
```

所以 60 bps 不是最终执行成本,只是已经量化出来的最低摩擦。真实执行门槛只会更高。

## 8. 怎么作为一篇打卡作业提交?

不要只写:

```text
我跑了两天数据,拿到跨资产门槛常态约 60 bps。
```

这样像流水账。

更好的主线是:

```text
我把一次报价升级成了分布观察,并用 98 次样本修正了早期错误判断。
```

可以按这个结构写:

```markdown
# Week 2 打卡:把一次报价变成分布观察

本次目标不是找一个单点好报价,而是验证 ARB.USDC ⇄ BAS.WETH 这条跨资产往返路径的真实成本常态。

## 方法

我用 `watch_probe.py` 在服务器上持续调用 `cost_probe.py`,每 30 分钟跑一次 LI.FI 只读报价。`cost_probe.py` 负责按 token 口径计算真实 bps 门槛,`watch_probe.py` 负责把每次结果写入 `watch/*.jsonl`。

监控路径:

- 稳定币对照组:`ARB.USDC -> BAS.USDC`
- 跨资产目标组:`ARB.USDC -> BAS.WETH -> ARB.USDC`

## 结果

跨资产往返路径已跑 48.5 小时,共 98 次观测:

- 1000 USDC:中位 60.45 bps,区间 [51.90, 73.31],标准差 2.94
- 10000 USDC:中位 60.84 bps,区间 [44.89, 70.52],标准差 3.54
- 前半 vs 后半中位差约 +1.17 bps,说明当前样本已经初步收敛

稳定币路径作为对照,98 次观测后仍稳定在约 25 bps,标准差接近 0。

## 更正

Week 1 早期基于 2-3 个采样点,我曾把跨资产路径概括成 29-43 bps 量级。服务器长跑后发现这是错误概括:早期低值只是极端样本,不能代表常态。

正确结论是:

> ARB.USDC ⇄ BAS.WETH 的真实门槛常态约 60 bps,不是 30 bps。

## 判断

这条数据暂时不能直接证明“有机会”,反而更像是在缩小搜索范围:以后只有当真实可成交价差长期超过 60 bps,这条路径才值得继续研究。若屏幕价差长期低于该门槛,则应记录为“可复现地不成立”。

## 后续

继续跑满三天,补齐样本。下一步要把真实可成交价差补进 `evidence.csv`,再判断净收益是否长期为正。同时注意:约 60% 的观测伴随 `toAmountMin > toAmount` 的上游数据异常,虽然不影响当前门槛计算,但需要在可信度里打折。
```

核心句:

```text
本次最大的收获不是“发现 60 bps”,而是发现 3 个采样点会把结论带偏;持续监控把一次报价变成了可复核的分布。
```
