## 一、数据回来了,先别急着算

三天跑完,`watch/*.jsonl` 里躺着 142 行。第一反应是"终于可以出结论了" ——
但在算任何东西之前,**要先问这批数据够不够格**。

### 检查 1:有没有缺

```bash
python3 watch_probe.py --from-chain ARB --to-chain BAS --token USDC --history
```

```
服务器段 142 条   08-03 08:34 ~ 08-06 07:04   跨度 70.5h
应有 142 轮,实有 142,缺 0
```

**70.5 小时、每半小时一轮 = 应该有 142 轮,实际就是 142 轮。**

> **为什么要算"应有多少轮"**:如果只看"有 142 条数据",你不知道这中间
> 有没有断过。断了 20 轮又补跑 20 轮,总数一样,但那 20 轮的空白期
> 可能正好是行情剧烈的时候 —— 你的样本就有了系统性偏差。

### 检查 2:估计收敛了没有

```
规模 10,000   n=142   中位 25.02   标准差 0.00
              前半中位 25.02 / 后半中位 25.02  →  差 +0.00 bps
```

**把样本一分为二,看前后两半的中位数差多少。** 差得很小 = 再多采样也不会变了。

这就是判断"够不够"的可计算标准,**不靠感觉**。

对比一下跨资产那条:

```
48.5 小时 (n=98)     中位 60.45
70.5 小时 (n=142)    中位 60.64      ← 多跑 22 小时,只动了 0.19 bps
```

**48 小时时判定的"已收敛"是对的。** 多跑的一天只是确认。

### 检查 3:数据干不干净

```bash
python3 make_evidence.py --since 2026-08-03T08:34:00Z
```

```
已排除 6 条 2026-08-03T08:34:00+00:00 之前的观测(正式监控前的调试数据)
```

**`--since` 切掉的是我在本地调试脚本时随手跑的那几轮。**

为什么要切?那几轮里有一次报出 22.59 bps,而服务器 142 轮的最低值是 49.24。
**一条调试残留就能把区间下沿拉低 27 bps**,让人误以为"这条路有时候能便宜到 22"。

> **调试数据不是观测数据。** 而且它们有个共同特征:**都是极端值** ——
> 因为你调试时测的就是边界情况。详见 [证据记录表教学](证据记录表教学.md)。

### ⚠️ 我在写这一节时,自己犯了正要警告的错

**第一版我是这么论证的:**

> 「同一小时跨日极差 **9~12 bps**,比不同小时之间的差 5.3 bps 还大」

举的例子是 02:00(9.3)、23:00(10.5)、21:00(12.4)。

**但那是我挑出来的三个最大值。** 看完整 24 行:跨日极差的**中位数只有 7.6**,
最小的 06:00 只有 0.8。**写"9~12"是在用极值冒充典型值** ——
和我正在批评的"从 24 个格子里挑出峰谷讲故事",是同一个毛病。

### 正确的做法:比较组间和组内的离散度

想问"小时之间的差异是不是真的",要比的是两个方差:

| | 含义 | 数值 |
|---|---|---|
| **组间** | 24 个小时中位数之间的标准差 | **1.43 bps** |
| **组内** | 同一小时内部(跨天)的合并标准差 | **2.98 bps** |

```
组间 / 组内 = 0.48
```

**小时之间的差异,只有小时内部随机波动的一半。**

用大白话说:**你在不同小时之间看到的那点差别,比同一个小时在不同天之间
的差别还小。** 那就不是规律,是噪声。

### 一个更严重的问题:这个设计根本没法做严格检验

我本来想跑个方差分析(ANOVA)给个 p 值,算出来 `F(23,118) = 1.74`,
刚好卡在显著性边缘。**但这个数字不能用**,因为采样设计有个硬伤:

```
0h  ~  7h   采自   08-04 / 08-05 / 08-06
8h  ~ 23h   采自   08-03 / 08-04 / 08-05     ← 不是同一批天!
```

而逐日中位数在**持续漂移**:

```
08-03  60.46      08-04  60.13      08-05  60.98      08-06  61.19
```

**早晨那几个小时多包含了最贵的 08-06,晚上那几个小时多包含了较便宜的 08-03。**
所以"小时效应"里混进了"日期效应",两者分不开 —— 这叫**混淆(confounding)**。

> **可迁移的一条:检验周期性之前,先确认每个周期格子里的样本
> 是不是来自同一批周期。** 监控跑了 70.5 小时,就注定了 0–7 点和 8–23 点
> 落在不同的日期集合上。
>
> 想做严格的日内分析:**跑满整数天并对齐日界**,或者按"日期 × 小时"双因素处理。
> (下面 📌 那节是数据跑齐后的复查 —— **"整数天"这个说法我当时说得不够精确**。)

### 📌 2026-08-07 复查:数据跑齐之后重做了一遍

上面说「想做严格日内分析,要么跑满整数天,要么按日期×小时双因素处理」。
数据补到 **84.7 小时** 之后回来重做,**发现我那句建议说得不够精确**。

#### 坑:精确 72 小时窗口 ≠ 消除混淆

从 84.7 小时里截出一个**正好 72 小时**的窗口(08-03 14:35 ~ 08-06 14:35),
每个小时的样本数确实齐了(全是 n=6)。但日期集合还是不同:

```
15h ~ 23h   来自 08-03, 08-04, 08-05
00h ~ 14h   来自 08-04, 08-05, 08-06
```

**因为窗口从 14:35 开始,日界(00:00 UTC)从中间切过去了。**

> **修正:必须是「整数天 **且** 对齐到日界」。**
> 只满足"整数天"不够 —— 窗口起点不在 00:00,各小时照样落在不同的日期集合上。
> 而 n 齐了反而更有迷惑性:看起来平衡,其实还是混的。

#### 两个正确做法,结果一致

**方案 A:只用完整的 UTC 自然日**(零混淆,代价是样本变少)

数据里完整覆盖 24 小时的只有 **08-04、08-05 两天**,每小时 n=4:

```
组间(24 个小时中位数的标准差)   1.98 bps
组内(同一小时内部的合并标准差)   2.95 bps
组间 / 组内 = 0.67
```

**方案 B:双因素 —— 先扣掉日期效应,再看小时效应**(用全部数据)

日期效应确实存在,而且在缓慢上漂:

```
08-03  60.46      08-04  60.13      08-05  60.98      08-06  61.15
```

每个观测减去当天中位数,残差里就只剩小时效应和噪声:

```
组间   1.29 bps
组内   3.23 bps
组间 / 组内 = 0.40
残差中位数跨度只有 5.26 bps
```

**两个方案都是组间远小于组内**(0.67 和 0.40),结论一致。

#### 最后补一个置换检验,拿到 p 值

前面都是比值,没有"这算不算显著"的判据。补一个**置换检验**:
把小时标签随机打乱 3000 次,看纯随机能不能产出同样大的比值。

```
观测到的 组间/组内     = 0.398
随机打乱 3000 次       中位 0.346   95 分位 0.443
p = 0.180
```

**3000 次里有 541 次(18%)能随机得到不低于实测的比值。**

> **p = 0.180,没有证据支持日内周期效应。**
>
> 注意这句话的措辞:是"**没有证据支持**",不是"证明了没有"。
> 样本只有 3~4 天,如果真存在一个 1~2 bps 量级的小时效应,这个样本量也看不出来。
> 但至少可以说:**没有大到值得据此择时的效应。**

#### 为什么置换检验比 ANOVA 好用

前面那个 `F(23,118)=1.74` 我判定不可用,因为混淆。而置换检验:

- **不需要假设正态分布**(成本分布是偏的,有路由降级造成的长尾)
- **不需要方差齐性**
- **直接回答那个问题**:"如果小时根本不重要,我看到这么强的模式的概率有多大?"

做法简单到可以手写:**把标签打乱,重算统计量,数一下有多少次超过实测值。**

> **可迁移的一条:分不清"是规律还是巧合"时,就把标签打乱几千次。**
> 这是最不需要前提假设的检验方法。

### 所以结论是什么

**没有可用的日内周期证据。** 三条独立路径都指向同一结论:

| 方法 | 结果 |
|---|---|
| 全部数据的组间/组内 | 0.48 |
| 只用完整自然日(零混淆) | 0.67 |
| 双因素扣掉日期效应 | 0.40 |
| **置换检验** | **p = 0.180** |

依据**不是**我第一版那个挑出来的"9~12 vs 5.3"(那是拿极值冒充典型值)。

**实践结论不变:别按时段择时。** 但理由要说对。

### 为什么这么容易上当

每个小时只有 **6 个样本**(3 天 × 2 个半小时点)。6 个数的中位数本来就抖。
24 个小时里总会有一个碰巧最高、一个碰巧最低 ——
**你一定能找出"跨度 5.3 bps"这种数字,哪怕数据完全是随机的。**

这叫**在噪声里找图案**。人脑特别擅长这个,所以必须用一个**可计算的检验**挡住它,
而不是靠"我觉得这个规律挺明显"。

这和之前学的几条是同一族防御:

| 场景 | 危险信号 | 挡它的检验 |
|---|---|---|
| 回测算出 100% 成功率 | 太好了 | 换个判据(收盘价而非最高价) |
| 用今天的榜单扫历史 | 样本全是幸存者 | 用历史时点的榜单 |
| 小时分布图有峰谷 | 有故事可讲 | **组间离散度 vs 组内离散度** |
| **举例支持自己的结论** | **例子都很有说服力** | **它们是典型值还是极值?** |

最后一行是这次新加的 —— **而且是我自己犯的**。

## 三、异常归因:一次 groupby 解决了待办里的大问题

跨资产那条路有个一直没解决的问题:

```
上游数据异常 82/142 (58%)
```

「异常」指 `toAmountMin > toAmount` —— **最低保证到手比预期到手还多**,
这在逻辑上不可能,说明报价数据自相矛盾。

三天下来比例没降(之前 60%),**是持续问题不是偶发**。

原计划是写个复杂的跨链版不变量检查去定位。但其实**数据里已经有答案了** ——
每条记录都存了走的是哪些桥,按桥分组数一下就行:

```
桥/工具                异常/总数    异常率
stargateV2            82/82        100%   ← 就是它
layerswap             31/51         61%
mayan                  6/9          67%
relaydepository       45/83         54%
mayanFastMCTP          0/57          0%   ← 完全干净
across                 0/1           0%
```

**`stargateV2` 出现 82 次,82 次全部异常 —— 100%。**
而 `mayanFastMCTP` 出现 57 次,**一次都没有**。

至于 `layerswap`(61%)、`relaydepository`(54%),它们不是自己有问题 ——
是**和 `stargateV2` 配对时**被带进去的。证据:总异常轮数 82,
正好等于 `stargateV2` 的出现次数,**一一对应**。

> **教训:动手写新工具之前,先看看现有数据能不能回答。**
> 这次省下了写跨链不变量检查的时间,而且答案更干脆。

## 四、核对自己填的数(这一步最容易跳过)

表填完之后,我把每个数字回原始文件重算了一遍。**发现两处问题。**

### 问题 1:中位数写错了 0.26 bps

```
表里写:  中位约 +3.77 bps
实际:    中位 +3.51 bps
```

差 0.26 bps,**对结论毫无影响**(离 60 bps 门槛还差 17 倍)。

那为什么还要改?

> 因为**表里的每个数字都应该能被复现**。今天差 0.26 无所谓,
> 但如果养成"差不多就行"的习惯,哪天差的就是 26。
>
> 而且三个月后你自己回来看,发现数字对不上,**你会开始怀疑整张表**。

### 问题 2:「链内离散度」其实只测了一半

表里写「只有 21/72 小时价差绝对值超过**链内场所离散度**」。核对时发现:

```
ARB_disp_bps 有值: 0/72     ← 全空
BAS_disp_bps 有值: 72/72
```

**Arbitrum 的备选池那 72 小时一笔成交都没有**,拉不到数据。所以这个比较
**只用了 Base 一侧的离散度**。

这不会推翻结论(如果 ARB 也有离散度,取两者最大值只会让"超过"的小时更少,
结论更强)。但**措辞会让人以为两条链都测了**。

改成:

> 只有 21/72 小时价差绝对值超过**同期 Base 链内**场所离散度
> (ARB 备选池该时段无成交,离散度缺失,故为单侧比较)

> **规则:局限要写在结论旁边,不要写在文档末尾。**
> 写在末尾等于没写 —— 引用的人只会复制那句结论。

## 五、最终的一行长什么样

```
时间        : 2026-08-03T08:34:57 ~ 2026-08-06T07:05:11
链          : ARB→BAS
资产        : USDC→WETH
类型        : 跨链·往返
规模        : 1000 USDC
观测次数     : 142
屏幕价差bps  : -26.31 ~ +26.49(可成交中间价,逐小时72h;中位约+3.51)
真实成本bps  : 60.64 [49.24~73.31]
净收益bps    : -86.95 ~ -34.15
延迟秒       : 37
成败原因     : 历史 72 小时跨链价差最大只有 +26.49 bps,中位约 +3.51,低于往返成本
              中位数 60.64;即使用最大屏幕价差减最低成本 49.24,仍为 -22.75 bps。
              且只有 21/72 小时价差绝对值超过同期 Base 链内场所离散度 ——
              屏幕价差本身不是稳定信号。
可复现       : 可复现地不成立(72小时历史价差从未穿过成本门槛;142次成本观测显示门槛约60bps)
```

### 净收益为什么用「中位成本 × 极值价差」

```
最差:  -26.31 (最小价差) − 60.64 (中位成本) = -86.95
最好:  +26.49 (最大价差) − 60.64 (中位成本) = -34.15
```

成本用**中位数**,价差用**极值**。为什么不都用极值?

因为「最大价差」和「最低成本」**几乎不可能同一时刻发生**。
两个极值相减会算出一个现实中不存在的场景,把结论说得比实际乐观。

用中位成本配极值价差,**隔离出的是价差的波动范围** —— 这才是你想知道的。

(所以我另外单列了一句「即使用最大屏幕价差减最低成本,仍为 −22.75 bps」——
**最乐观的假想场景下依然为负**,这是压力测试,不是主结论。)

### 「成败原因」里最值钱的一句

> 屏幕价差**本身不是稳定信号**

注意它说的**不是**「价差不够大」,而是「价差这个量在这个尺度上没有意义」。

因为 51/72 小时里,跨链价差比**同一条链上不同池子之间的差**还小。
这时候「Base 上 WETH 的价格」根本不是一个数字 —— 你换个池子比,
+26 bps 就能变成 −2 bps。

**这是结构性判断,不是当日观察。** 结构性判断才能推广到别的路径。

## 新手最容易犯的四个错

### 1. 数据一到手就开始算

先验数据够不够格:**缺没缺、收敛没有、干不干净**。
在坏数据上算出的漂亮结论,比没有结论更糟。

### 2. 看到分布图就讲故事 —— 而且举例时还挑最有利的

任何 24 个格子的图,总有最高和最低。**讲故事之前先做组间/组内比较。**

**更隐蔽的一层**:我写这篇时,第一版拿"极差 9~12 bps"当证据 ——
那是从 24 个小时里挑出的三个最大值,而中位数只有 7.6。
**用极值冒充典型值,和用峰谷讲故事是同一个毛病**,只是套了层"我在做检验"的外衣。

判据很简单:**你举的例子,是不是全体的典型?** 不确定就报中位数和分布,别举例。

### 3. 自己填完的数不回头核对

今天核对出两处 —— 一处算错、一处措辞过宽。
两处都不影响结论,但**不核对你就不知道它们不影响**。

### 4. 把局限写在文末

「ARB 离散度缺失」如果只写在末尾的局限章节,引用的人只会复制那句
「21/72 小时超过链内离散度」。**局限要贴在结论旁边。**

## 一句话总结

前三篇教的是**怎么把数据弄到手**,这一篇教的是:

```
数据 ≠ 结论。中间隔着四道检验:
  够不够(缺失 / 收敛)、干不干净(调试数据)、
  是不是规律(跨周期一致性)、算没算对(逐项复核)。
```

**今天真正的产出不是"两条路都不成立",是那个被拆掉的日内周期故事。**
结论会过期(费率变了、行情变了),但"挑出规律前先做跨周期检验"这个动作不会。
