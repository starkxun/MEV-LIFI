# 服务器拉取数据教学:到底在拉什么,有什么用

> 配套操作手册: [`服务器拉取数据.md`](./服务器拉取数据.md)  
> 核心脚本: [`watch_probe.py`](../../watch_probe.py)  
> 成本计算来源: [`cost_probe.py`](../../cost_probe.py)

## 先给结论

这里说的"服务器拉取数据",不是拉你的钱包数据,也不是抓真实链上成交数据。

它做的是:

> 定时向 LI.FI 报价接口要报价,然后把每次报价算成一条"成本观测记录"。

你可以把它理解成服务器每半小时问一次 LI.FI:

> 如果现在从 Arbitrum 把 1000 或 10000 USDC 换/跨到 Base,系统会给我什么路线?
> 预计到手多少?成本是多少?要多久?用哪个桥或聚合器?

脚本不会发交易,不会动钱包里的钱。它只是读报价。

---

## 它具体拉哪两类数据

文档里启动了两个 tmux 窗口,对应两条路径。

### 1. 稳定币路径:ARB.USDC -> BAS.USDC

命令核心是:

```bash
python3 -u watch_probe.py --from-chain ARB --to-chain BAS --token USDC \
  --amounts 1000,10000 --interval 1800 --alert-below 20
```

这条路径的意思是:

```text
Arbitrum 链上的 USDC -> Base 链上的 USDC
```

这是"同资产跨链",起点和终点都是 USDC,所以成本很好算。

例如:

```text
投入 10000 USDC
最后到手 9975 USDC
少了 25 USDC
成本 = 25 / 10000 = 0.25% = 25 bps
```

这里的 `bps` 可以先理解成"万分之几":

```text
1 bps = 0.01%
25 bps = 0.25%
100 bps = 1%
```

这条稳定币路径主要用来做对照组。

### 2. 跨资产往返路径:ARB.USDC -> BAS.WETH -> ARB.USDC

命令核心是:

```bash
python3 -u watch_probe.py --from-chain ARB --to-chain BAS \
  --from-token USDC --to-token WETH --amounts 1000,10000 \
  --roundtrip --interval 1800 --alert-below 25
```

这条路径的意思是:

```text
第一步:Arbitrum USDC -> Base WETH
第二步:Base WETH -> Arbitrum USDC
```

为什么要做往返?

因为 `USDC -> WETH` 是跨资产,起点和终点不是同一种东西。
如果只看单程,你会遇到一个问题:

```text
我投入的是 USDC
到手的是 WETH
那到底亏了多少 USDC?
```

这个问题会牵涉 WETH 价格。如果价格口径处理不好,成本就会算歪。

所以脚本采用"闭环"算法:

```text
先把 USDC 换成 WETH
再把这笔 WETH 原样换回 USDC
最后看少了多少 USDC
```

这样起点和终点又都是 USDC,成本就能直接算。

## 每次拉取后会存什么

`watch_probe.py` 会把每轮结果写进 `watch/*.jsonl`。

当前这两条路径对应两个文件:

```text
watch/ARB.USDC-BAS.USDC.jsonl
watch/ARB.USDC-BAS.WETH-rt.jsonl
```

`jsonl` 的意思是:一行就是一条 JSON 记录。

每一行大概记录这些字段:

| 字段 | 含义 |
|---|---|
| `ts` | 这次观测的时间 |
| `from_chain` | 起始链,比如 `ARB` |
| `to_chain` | 目标链,比如 `BAS` |
| `from_token` | 起始资产,比如 `USDC` |
| `to_token` | 目标资产,比如 `USDC` 或 `WETH` |
| `roundtrip` | 是否是往返闭环 |
| `best_size` | 这轮里成本最低的资金规模 |
| `best_bps` | 这轮的最低总成本,单位 bps |
| `hard_bps` | 真实少掉的 token 成本 |
| `offchain_bps` | gas 等账外成本折算后的成本 |
| `tools` | LI.FI 选的路线/桥,比如 `eco`、`stargateV2`、`across` |
| `duration_s` | LI.FI 估算的执行时间 |
| `warnings` | 上游报价有没有异常 |
| `all_sizes` | 1000、10000 两个规模分别是多少成本 |
| `failed_sizes` | 哪些规模报不出价 |
| `alerts` | 是否触发告警 |

所以,"拉取数据"更准确的说法是:

> 定时拉 LI.FI 的当前报价快照,并把它加工成"这条路径当前成本是多少"的历史记录。

## 这些数据有什么用

最重要的用途是:判断一条路径是不是稳定、可复现、值得继续研究。

单次报价没有太大意义。

比如你现在问一次 LI.FI,发现成本是 `22 bps`,这可能代表很多情况:

```text
可能是真实长期水平
可能是短暂好机会
可能只是报价噪声
可能是路由临时切换
可能是上游数据异常
```

你只看一次,分不出来。

所以文档让服务器跑三天,每半小时一次。这样你会得到很多观测点。

三天后,每条路径大约有:

```text
24 小时 / 0.5 小时 = 48 次
48 次 * 3 天 = 144 次观测
```

有了这些样本,你才能回答:

```text
这条路径平时成本是多少?
最低能到多少?
最高会飘到多少?
路由会不会经常变?
1000 USDC 和 10000 USDC 成本差别大不大?
它是不是偶尔才好,还是经常都好?
```

这就是 `evidence.csv` 里"可复现?"这一列需要的依据。

## 为什么稳定币路径是对照组

稳定币路径:

```text
ARB USDC -> BAS USDC
```

理论上成本主要来自固定费率和桥费,变化应该很小。

跨资产往返路径:

```text
ARB USDC -> BAS WETH -> ARB USDC
```

里面有市场撮合、兑换、桥、实时路由,变化应该更大。

所以稳定币路径的作用像实验里的"参照物"。

如果你看到:

```text
稳定币成本一直在 25 bps 左右
跨资产成本在 22 到 43 bps 之间跳
```

那说明跨资产路径确实受市场和路由影响更大。

如果跨资产路径也几乎不动,那反而是一个新发现:

```text
它可能不是你以为的市场波动型机会,而是某种稳定费率结构。
```

## 为什么要看路由 tools

`tools` 字段记录 LI.FI 这次选择了哪个桥或工具。

例如:

```text
eco
stargateV2 -> across
```

这很重要,因为成本一样不代表风险一样。

例如:

```text
路线 A:成本 25 bps,预计 7 秒
路线 B:成本 25 bps,预计 1080 秒
```

表面看成本一样,但执行风险完全不同。时间越长,价格变化、失败、卡住的风险就越大。

所以脚本不只记录 `best_bps`,也记录 `tools` 和 `duration_s`。

---

## 为什么要设置告警阈值

文档里有两个阈值:

```text
稳定币路径:alert-below 20
跨资产往返:alert-below 25
```

告警不是为了每次都响,而是为了捕捉"有意义的变化"。

稳定币路径平时大约在 25 bps 附近,如果设置成 25,可能会经常响,最后你会开始无视它。

所以稳定币设成 20:

```text
如果稳定币路径跌破 20 bps,说明费率结构可能真的变了。
```

跨资产往返路径波动更大,设成 25 是为了捞到成本偏低的一侧:

```text
如果跨资产闭环成本低于 25 bps,可能出现了值得看的窗口。
```

## logs 和 watch 的区别

文档里同时有 `logs/` 和 `watch/`。

它们不是一回事。

### logs/*.log

这是过程日志,给人排查用。

例如:

```text
logs/stable.log
logs/roundtrip.log
```

它记录程序运行时打印了什么、有没有报错、有没有告警。

这类文件不进 git。

### watch/*.jsonl

这是证据数据,给后面分析用。

例如:

```text
watch/ARB.USDC-BAS.USDC.jsonl
watch/ARB.USDC-BAS.WETH-rt.jsonl
```

它是结构化记录,可以被脚本读取、统计、写进证据表。

这类文件是研究证据,应该跟踪提交。

## 和 make_evidence.py 的关系

三天数据攒够后,文档让你跑:

```bash
python3 make_evidence.py --dry-run
python3 make_evidence.py --fetch-screen
```

意思是:

```text
先根据 watch/*.jsonl 的历史观测,生成证据记录表的建议。
再补充屏幕价差等辅助信息。
```

到那时,跨资产那一行的"可复现?"就不是靠感觉填,而是靠历史样本填。

## 新手版一句话总结

`watch_probe.py` 做的不是交易,而是监控报价。

它每隔半小时问 LI.FI:

```text
现在这条路径走哪条路?
成本是多少?
预计多久?
1000 和 10000 两个规模哪个更划算?
有没有异常?
```

然后把答案存到 `watch/*.jsonl`。

这些历史记录的用途是:

```text
把"我看见过一次好报价"变成"这条路径经过多次观测后确实有规律"。
```

这就是后面判断套利机会、填写证据表、判断是否可复现的基础。
