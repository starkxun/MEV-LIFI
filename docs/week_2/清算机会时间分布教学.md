# 清算这门生意什么时候开张 —— 两轮验证

> 打卡日期:2026-08-10
> 脚本:[`oracle_lag.py`](../../oracle_lag.py)
> 数据:180 天 3,450 笔清算 + 爆发日预言机时差
> 前置:[研究人教学](研究人教学.md)、[论文与实测对照](论文与实测对照.md)

这篇回答一个很具体的问题:

> **清算机会是天天都有,还是集中在少数几天?**

因为这个答案决定了你该优化什么 —— **优化平均速度**,还是**优化"关键那几天系统还活着"**。

---

## 先给结论

```
180 天,3,450 笔清算

最忙的 1 天  →  32.3% 的清算    ← 一天占掉三分之一
最忙的 3 天  →  45.4%
最忙的 5 天  →  53.6%

中位数天 6 笔    最忙一天 1,114 笔    相差 186 倍
```

**这门生意一年只开张几天。** 而且更反直觉的是:

```
爆发日的参与者反而更少(56 个,而全期有 207 个)
爆发日的预言机领先窗口反而更宽(78% 领先,vs 平静日 63%)
```

用一句话概括:**熊市练技术,牛市大杀四方 —— 但练的不是技术,是"那几天系统还活着"。**

---

## 一、为什么要问这个问题

上一轮我们扫了 2 天,得出:

```
ETH 1.5 笔/天    ARB 2.0    BASE 4.0
清算人:ETH 3 个、ARB 3 个、BASE 只有 2 个
```

看着像个「机会很少但竞争也很少」的小生意。

**但 2 天的样本能说明什么?** 按这个项目一路的规矩,答案是:什么也说明不了。清算是**波动的函数** —— 价格不动就没有仓位跌破清算线。2 天平静期的数据,是**下界**,不是常态。

所以要扫一段**足够长、且包含大跌**的窗口。

---

## 二、怎么扫:先测工具的边界

想扫 180 天,第一步不是写循环,是**问清楚一次能扫多少**:

```
ETH   2,000 块 ✓    10,000 块 ✓    50,000 块 ✗ Block range is too large
ARB   同上
BASE  同上
```

**上限 10,000 块。** 这个数决定了扫描成本:

| 链 | 出块 | 10,000 块 = | 扫 180 天需要 |
|---|---|---|---|
| **ETH** | 12 秒 | **1.4 天** | **130 次请求** ✅ |
| BASE | 2 秒 | 0.23 天 | 780 次 |
| ARB | 0.25 秒 | 0.03 天 | 6,200 次 ❌ |

**所以选以太坊。** 不是因为它最重要,是因为**它最便宜扫** —— 出块慢反而成了优势。

实际耗时:130 次请求 **33 秒**,拿到 3,450 条。

> **可迁移的一条:先测工具边界,再设计方案。**
> 如果一开始就闷头写 Arbitrum 的扫描,6,200 次请求跑半小时,还可能中途被限速。

## 三、结果一:时间集中度极端

### 数字

```
有清算的天数     161/180  (89%)   ← 大部分日子都有一点
最忙 1 天        32.3% 的清算
最忙 3 天        45.4%
最忙 5 天        53.6%
最忙 10 天       61.7%

中位数天 6 笔    最忙一天 1,114 笔    基尼系数 0.760
```

**89% 的日子都有清算,但一半的清算挤在 5 天里。**

### 爆发是连着来的

```
2026-06-02   166 笔
2026-06-03   115
2026-06-04   252
2026-06-05  1114   ← 峰值
2026-06-06   202
────────────────
五天合计 1,849 笔 = 全部的 54%
```

**不是一天,是一场持续五天的连锁。** 这符合论文里那篇 Hawkes 过程的说法 —— 清算会**自我激发**:清算 → 抛售抵押物 → 价格更低 → 更多仓位跌破线。

### 爆发日内部还在集中

```
2026-06-05 逐小时:
  06h  259 笔 ██████████████████████████████████████████████
  15h  148 ██████████████████████████
  05h  138 ████████████████████████
  14h  125 ██████████████████████
  ...
  09h~11h  0 笔
```

**最集中的一小时占当天 23%。**

所以真实的时间尺度是:**一年 → 5 天 → 几个小时**。

## 四、结果二:爆发日参与者反而更少

这条最反直觉,而且**我第一次说错了**。

我看到"全期 207 个清算人"就说「爆发日 200 多个玩家全部上线」。查当天数据:

```
全期 180 天        207 个清算人
其余 179 天        196 个
爆发日当天          56 个   ← 只有四分之一
只在爆发日出现的     11 个
```

**爆发日只有 56 个参与,而且集中度更高**(前 10 名占 68.5%)。

### 怎么解释

平时 6 笔/天,任何一个能跑的机器人都能捡到一两笔 —— 所以 179 天累计出现 196 个不同地址。

但 1,114 笔涌进来那天,**大部分机器人反而消失了**。可能的原因:

- RPC 被打爆、节点跟不上
- gas 估算失败、余额不够
- 合约在极端参数下 revert
- 干脆没在跑

**这正是「练技术」的含义** —— 不是练速度,是练**极端负载下不掉线**。

> **可迁移的一条:平均值会骗人,极端值才是考题。**
> 一个 99% 时间正常、1% 时间掉线的系统,在这门生意里等于没做。

---

## 五、结果三:预言机窗口在爆发日**没有被压缩**

这是最关键的一测。

背景:上一轮我们验证了论文说的「Optimism 的预言机是其它链的领先指标」,平静日测出 **63% 领先、中位 31 秒**。

但当时留了个担心:

> 平静期更新稀疏,窗口才宽。**真到爆发日,大家都在抢,窗口会不会压缩到 2 秒?**

回溯 2026-06-05 实测:

| | 平静日 | 爆发日 24h | 爆发峰值 1.5h |
|---|---|---|---|
| OPT→ARB | 63% / 31s | **78% / 34s** | **80% / 32s** |
| OPT→BASE | 61% / 54s | **69% / 48s** | 69% / 46s |

**领先比例反而升高(63% → 78%),秒数基本不变。**

而且这还是**低估** —— 979 次事件里有 163 次是「300 秒内目标链根本没穿过」,被我保守地排除了。

### 这意味着什么

```
你在 OPT 上看到 ETH 跌破某个价位
     ↓  中位 34 秒之后
ARB 上的预言机才认为价格到了那里
     ↓
这 34 秒里,ARB 上哪些仓位会变得可清算,你已经算得出来
```

**34 秒在 MEV 里是极长的时间。** 而且这条信息是**公开的** —— 不需要任何私下关系,谁都能读 Optimism 的预言机。

## 六、结果四:试错几乎免费

论文说 L2 上的投机型清算人靠**疯狂发重复交易**抢机会,回滚率 95%+。实测那个被点名的 Arbitrum 机器人:

```
600 笔样本
  回滚      544 笔 (90.7%)   单次 $0.0084
  空转成功   56 笔 ( 9.3%)   单次 $0.0293
  真实清算    0 笔
```

```
连失  20 次 = $0.17
连失 100 次 = $0.84
连失 200 次 = $1.69
```

**成本完全不是门槛。** 按平静期 600 笔/天算,年空转成本约 **$850**。

### 但这里有个必须说清的发现:`status=0x1` ≠ 成功清算

我一开始按交易状态分类,算出"56 笔成功、中位利润 −$0.03"。查下去发现**这 56 笔里一笔清算都没有**,日志数中位 **0 条** —— 纯空转。

论文其实写了这一点:

> 这些交易只是**读取状态**来识别机会,当没有可盈利机会时**不执行任何状态改变就终止**

所以真实构成是:

```
90.7%  回滚
 9.3%  执行成功但什么也没做
 0.0%  真的清算了       ← 那天(平静日)一笔都没有
```

**这不是"策略不行",是"这门生意那天没开张"。**

## 七、我在这两轮里踩的三个坑

### 坑 1(最严重):Chainlink 会轮换聚合器合约

回溯爆发日时,Optimism 显示 **0 次预言机更新**,而同期 Arbitrum 有 344 次。

**"某条链那天没数据"看起来完全合理** —— 可能是喂价没更新、可能是链不活跃。差点就这么算了。

真实原因:

```
Chainlink 用 phase 机制轮换底层聚合器
  代理地址(proxy)不变
  但事件是由**当时那个聚合器**发出的

我用 aggregator() 拿的是**当前**那个
→ 回溯到 3 个月前,它当时还没上线
→ 自然一条事件都没有
```

修法:用 `phaseId()` + `phaseAggregators(uint16)` 枚举全部历史聚合器,一次查询传数组。

**OPT 从 0 次 → 163 次。**

> **可迁移的一条:代理合约背后的实现会换。**
> 回溯历史数据时,不能假设"现在指向谁,过去就是谁"。
> 而且这类错误的表现是**数据缺失**,不是报错 —— 最容易被当成"那天就是没有"。

### 坑 2:配对方法制造了假象

第一版量时差用的是「**按价格配对**」:找价格最接近的那次更新,量时间差。

```
跑出来:88% 领先,平均 74.3 秒
论文:  66.5% 领先,平均 19.4 秒
```

**比论文强 4 倍 —— 这才是危险信号。**

原因:

```
ARB 每 61 秒更新,OPT 每 176 秒
→ 0.15% 容差内有好几条 ARB 候选
→ 按"价格最接近"挑,可能挑到时间上很远的那条
→ 系统性夸大领先量
```

改成论文实际用的**阈值穿越法**(参考链变动 ≥5 bps → 目标链多久后穿过同一价位),立刻回落到 63% / 31 秒,和论文一致。

> **结果"太好"要先怀疑方法,不是庆祝。**
> 这是本项目第四次:100% 回测成功率、天文数字价格、伪零、现在这个配对假象。

### 坑 3:我把"全期人数"当成了"当天人数"

看到 207 就说"爆发日 200 多人上线"。实际当天只有 56 个。

**这是个很低级的错** —— 把一个跨 180 天的累计值,当成了某一天的瞬时值。

> 而且它恰好把结论**推向了相反的方向**:如果真是 207 人抢,这门生意就没戏了;
> 实际 56 人,而且多数平时活跃的反而没出现 —— 这才是有利信号。

## 九、所以「原型」到底做什么

不是完整机器人。按现在验出来的东西,核心只有一件事:

> **在 OPT 预言机更新后、ARB 预言机更新前的那 34 秒里,
> 能不能算出哪些仓位即将可清算,并把交易准备好。**

分三阶段,**做到 P1 就算通过**:

| 阶段 | 做什么 | 发交易? | 工作量 |
|---|---|---|---|
| **P0 影子模式** | 监听 OPT 预言机 → 用新价格重算 ARB 上所有仓位健康度 → 记录"谁将要可清算" | ❌ 只记录 | 3~5 天 |
| **P1 模拟验证** | 对每个目标用 `eth_call` 模拟清算,验证真的会成功 | ❌ 只模拟 | 3~5 天 |
| **P2 小额实盘** | 部署合约,闪电贷+清算+RFQ 变现打包一笔 | ✅ 亏得起的量 | 可能超期 |

**P0+P1 跑完能回答成本模型里最后一个「待定」项:失败交易概率。** 而且全程不花钱、不担风险。

## 新手最容易犯的四个错

### 1. 用平静期的数据判断一门"看波动吃饭"的生意

2 天样本说"每天 1.5 笔、只有 3 个竞争者"。180 天样本说"一天 1,114 笔、207 个竞争者"。
**两个都是真的,但只有后者能用来做决策。**

### 2. 把累计值当成瞬时值

"180 天里出现过 207 个清算人" ≠ "某一天有 207 个在抢"。
**这个错会让你把有利结论读成不利结论。**

### 3. 认为"没有数据"就是"那天没发生"

Optimism 那 0 次更新是扫错了合约。
**代理合约背后的实现会换 —— 回溯历史时必须枚举历史版本。**

### 4. 结果比预期好的时候不去查

88% / 74 秒比论文强 4 倍,当时完全可以直接写进结论。
**"太好"和"太差"一样值得怀疑。**
