## 先纠正一处事实

共学文档第 37 行写着:

> **onChainListen(Go / PostgreSQL 链上管道)**

**实际不是这样。** 实测 `~/onChainListen`:

```
Go 文件:      0 个
Postgres 引用: 0 处
实际构成:      ~30 个 Python 脚本 + web3.py,结果落 JSON / JSONL / TSV 文件
```

它是一套**基于 RPC 的链上扫描工具集**(扫桥风险、借贷市场、金库、任意转账后门),
不是数据库管道。这个区别很重要:

- ❌ 原计划"接现成的 PostgreSQL 查询" —— **没有库可接**
- ✅ 实际能接的是"**轮询采集的骨架**" —— 这个确实是现成的,而且正是监控需要的

所以复用的方式变了:不是接数据源,是**接采集模式**。

> 顺带一提,这本身就是共学的方法在起作用:**先验证再规划**。
> 如果直接照着文档去写 `psql` 查询,会浪费半天才发现库不存在。

## 从 onChainListen 复用了什么

只抄骨架,不抄业务。`poll_new_pools.py` 是用来盯"新池子"的,
但它里面有五样**任何长期轮询任务都要重写一遍**的东西:

| 复用的东西 | 原用途 | 现用途 |
|---|---|---|
| checkpoint 断点续跑 | 记住扫到哪个块高 | 记住上轮的门槛值,用来做变化对比 |
| 去重 SeenSet | 同一个池子不重复报 | 同一个观测不重复记 |
| 轮询循环 | 每 60 秒扫一次新块 | 每 N 分钟跑一次成本探针 |
| **单轮异常不拖垮整个循环** | 一条链挂了其他链继续 | 一次限速不该让盯了三天的进程死掉 |
| JSONL 追加 | 新池子落盘 | 门槛历史落盘 |
| `derive_rpc` 换链 | 一个 Alchemy key 盯多条链 | 同上,链上交叉验证时用 |

落成 [`lib/chainkit.py`](../../lib/chainkit.py)。

**没抄的**:所有扫描业务逻辑(topic0 抽址、金库风险规则、借贷预言机解析)。
那些跟成本核算无关,抄过来只会变成死代码。

> 值得单独说的是"单轮异常不拖垮循环"这一条。这是 onChainListen 里最有价值的
> 一行工程经验 —— 长期监控的第一杀手不是逻辑错误,是**某次网络抖动让进程静悄悄死了**,
> 而你三天后才发现。

## 新增的两个东西

### 1. `lib/chainkit.py` —— 采集基础设施

```python
from lib.chainkit import Checkpoint, SeenSet, append_jsonl, run_loop, eprint
```

还带了一个 `erc20_balance()`,用途是**用链上真实储备交叉验证 LI.FI 报的滑点**。
LI.FI 说这个规模滑点 5 bps,池子里到底有多少钱撑得住?自己去链上看一眼。

> 这是铁律 2 在数据源层面的版本:**报价接口也是一块屏幕,一样要复核。**

（这部分需要 `pip install web3`,是按需导入的;只跑 LI.FI 监控不需要装。）

### 2. `watch_probe.py` —— 持续监控

```bash
# 跑一次(给 cron 用)
python3 watch_probe.py --from-chain ARB --to-chain BAS --token USDC \
    --amounts 1000,10000 --alert-below 20

# 前台每 10 分钟一轮
python3 watch_probe.py --from-chain ARB --to-chain BAS --token USDC \
    --amounts 1000 --interval 600

# 看历史统计(不发新请求)
python3 watch_probe.py --from-chain ARB --to-chain BAS --token USDC --history
```

它 import `cost_probe.py`,**不重写任何成本逻辑**。改探针的算法,监控自动跟着变。

输出:`watch/<路径>.jsonl` + 人类可读摘要 + **退出码 10 表示有告警**。

三种告警对应三种现实:

| 告警 | 含义 |
|---|---|
| 门槛跌破阈值 | 机会窗口可能开了 |
| 门槛突变 | 路由或深度出事了,可能是机会也可能是陷阱 |
| **路由切换** | Week 1 学到的:`eco` 7秒 → `polymerStandard` 1080秒,门槛一模一样。**成本没变不等于风险没变** |
| 上游数据异常 | LI.FI 返回自相矛盾数据,这轮打折扣 |

## 三个 Hermes 技能

装在 `~/.hermes/skills/mev-lifi/`,源文件在 [`hermes/skills/`](../../hermes/skills/)(跟着 git 走)。

| 技能 | 干什么 |
|---|---|
| `mev-cost-probe` | 算任意路径的真实 bps 门槛 |
| `mev-spread-watch` | 持续监控 + 历史统计 |
| `mev-evidence-log` | 按证据表 schema 存档 |

验证已装上:

```bash
hermes skills list | grep mev
```

应该看到三行 `mev-lifi ... enabled`。

改了源文件之后重新安装:

```bash
cd ~/MEV-LIFI && cp -r hermes/skills/* ~/.hermes/skills/mev-lifi/
```

### 技能里最重要的不是命令,是纪律

技能文件里真正值钱的是那些**约束 Hermes 别犯错**的规则:

- 「**永远不要**引用 `fromAmountUSD` / `toAmountUSD` 得出成本结论」
  —— 防止它掉进你 Day-0 已经证伪的美元幻觉
- 「跨资产单程模式下脚本拒绝给门槛,这是设计不是 bug,不要绕过」
  —— 防止它"帮你解决问题"时把正确性绕掉
- 「没有历史数据**不要填**「可复现」列」
  —— 防止它用一次观测下结论
- 「统计时把负净收益的行也算进去」
  —— 防止幸存者偏差

> **这才是把 Agent 接进研究流程的正确方式**:不是让它更能干,是让它
> **在你已经踩过的坑上不再踩一遍**。你 Week 1 的每个教训,都该变成技能文件里的一行约束。
